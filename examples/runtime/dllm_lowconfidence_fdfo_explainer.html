0. 先记住这一句

LowConfidence 是「这一块里哪些 MASK 可以变成真正 token」的选词规则； FDFO 是「这一步算完要不要立刻把请求交还调度器」的调度规则。 两者正交：选词策略可以不变，只改调度，就能让快请求不再陪慢请求耗着。

PR #17770 当时把二者捆成 LowConfidenceFDFO。当前主线已经拆开： --dllm-algorithm LowConfidence 管选词， --dllm-fdfo（默认开）管调度。 原理仍是同一件事。

教学里我们用 block_size = 8，算法和 32 完全一样，只是格子更少、更好盯着看。 一次「去噪步」= 一次模型 forward + 一次按规则揭 MASK。

2. LowConfidence 算法：高置信就揭，否则揭最有把握的那一个

对当前块里每个还是 MASK 的位置：

x[i] = argmax(logits[i]) # 该位置最可能的 token
p = softmax(logits)
conf[i] = p[i, x[i]] # 这个预测有多自信
conf[~mask] = -inf # 已经揭开的位置不再改
transfer = conf > threshold # 默认 threshold = 0.95
if transfer 全 False: # 这一步谁都不够自信
transfer[argmax(conf)] = True # 保底：揭开置信最高的 1 个
所以「简单位置」可以一步揭好几个；「难位置」长期低于 0.95，每步只揭 1 个。 一块 8 个 MASK，最好 1 步结束，最坏 8 步（每步只揭 1 个）。这就是快慢分化的根源。

对应实现就在 python/sglang/srt/dllm/algorithm/low_confidence.py 的 step()：它只改 forward_batch.input_ids，不负责调度。

4. 原来的实现：选词循环关在 algorithm.run() 里

PR 之前（以及现在的 --no-dllm-fdfo 同步路径）把「把当前块去噪完」写成一个内层循环。 控制权要等 batch 里每一条请求的当前块都没有 MASK 才还给调度器。 

def _run_sync(...):                          # 现在的 base.py，语义等于原来的 LowConfidence.run
    out = model_runner.forward(...)
    for _ in range(block_size + 1):
        done = self.step(...)                # LowConfidence 揭一批 MASK
        if all(done):                        # ← 短板：必须全员完成
            break
        out = model_runner.forward(...)      # 快请求已经没 MASK 了，仍被带着再 forward
    return 整块 token                        # 这时才回 scheduler，才提交 output
all(done) 就是同步屏障。A 第 3 步已经揭完，仍要陪 C 再跑 5 次 forward； A 的 token 也不能提交、不能开下一块、更不能把 GPU 槽位让给排队的 D。

5. 问题长什么样：队头阻塞（Head-of-Line Blocking）

三个在跑、一个在排队。GPU 只有 3 个槽。A 快、C 慢。

同步 LowConfidence

当前波必须跑 max(3,5,8) = 8 步。A、B 提前结束也出不去。D 只能等这一波全部提交之后再上。

A 的延迟 = 8（自己只要 3）
D 的开始时间 = 8

你马上会看到的 FDFO

每 1 步都回调度器。A 第 3 步离开，D 立刻补位。C 继续慢慢揭，不再挡别人。

A 的延迟 = 3
D 的开始时间 = 3

PR 在 H800 / LLaDA2.0-mini / GSM8K 上相对同步 LowConfidence： BS=4 约 2.4×，BS=16 约 4.1×。 batch 越大，快慢差被放大得越厉害，FDFO 收益越大。

6. FDFO 怎么拆屏障：一步一调度

def _run_fdfo(...):
    out = model_runner.forward(...)          # 只做 1 次
    done = self.step(...)                    # 只揭 1 轮 MASK
    accept_length = [block_size if d else 0 for d in done]
    return 当前块快照, accept_length         # 立刻回 scheduler

调度器看 accept_length：

  • = block_size：这块已经没有 MASK（进入 step 时已完成，KV 是最终态）→ 提交 token，请求可开下一块或结束，槽位释放。
  • = 0：还没揭完 → 把半成品写入 dllm_incomplete_ids，下一轮带着半成品再来。
选词规则仍是 LowConfidence，一个 token 都没改。变的是： 去噪循环从 kernel/algorithm 内层，搬到了 scheduler 外层。 快请求「先做完就先出队」，所以叫 First Done First Out。

8. 调度器每一轮怎么给请求分类

PR 把每条请求在「这一次 forward 之后」分成四种去向。核心是：半成品不要当完成，完成了的不要继续占着当前块。

1 · Complete Prefill

当前块是 prompt 块，已经填完

还没有生成新 token。用 origin_ids 推进 fill_ids，继续下一块 prompt，或转入 decode。

2 · Incomplete Decode

decode 块里还有 MASK

accept_length = 0。写入 dllm_incomplete_ids（半成品 token + 仍在的 MASK），下一 round 原样填回去继续揭。

3 · Complete Decode，KV 还没落稳

MASK 刚揭完，但缓存尚未按最终 token 提交

PR 里仍走 incomplete 路径，避免用 MASK 块去当 prefix cache 的 key。当前主线会把未完成块的 KV 留下来复用，这是后续优化，语义不变。

4 · Complete Decode，KV 已更新

这块可以提交了

把输出 append 到 output_ids，检查 EOS / 长度。没结束就追加下一块全新 MASK，进入下一 decode 块。

调度（FDFO 改这里）

base.py
  fdfo  → _run_fdfo：forward 1 次就返回
  sync  → _run_sync：内层循环直到 all(done)

scheduler mixin
  accept_length == 0 → dllm_incomplete_ids
  accept_length == block_size → 提交 / 结束 / 下一块
回看 PR 标题 first done first out：不是改生成质量，是改「谁可以离开 batch」。 LowConfidence 决定一块要跑多少步；FDFO 决定这些步要不要锁在一起跑。
